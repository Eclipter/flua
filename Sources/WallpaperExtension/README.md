# Wallpaper extension

This is the native macOS wallpaper provider embedded in Flua, with a separate standalone fixture and test build. It can create a remote Core Animation context backed by an IOSurface, return a snapshot, accept locked/suspended updates, and supply a nonempty settings catalog using Apple's actual private payload classes.

A sandbox-signed disposable copy passed WallpaperAgent selection, context creation, snapshots and looping video on arm64 macOS 27.0.1 (26A434). A separate probe verified sandboxed access to external image/video fixtures through the host's file wrappers. During a real lock/unlock check, host updates were recorded and the user confirmed visible video motion on the Lock Screen. Real screen-saver transitions with video Animated/Still and aurora Still, plus aurora Still during explicit lock/unlock, passed the scoped check below. Broader hardware/OS behavior remains unverified. Flua writes `catalog.json` beside `library.json`, including speed, dimming, fit, trim, still-frame time, and desktop and Lock Screen modes, plus the four built-in scenes with no media file. The provider lists those image, video and scene entries from `FLUA_CATALOG`, a bundled `catalog.json`, the absolute Info.plist key `FLUACatalogPath`, or, when the bundle is an appex, `~/Library/Application Support/Flua/catalog.json`. If that file is not readable, the provider asks the host for read-only access, retrying failed requests and pushes an updated settings catalog. A later write or atomic replacement of that catalog file pushes again. Media bytes still arrive as host file wrappers. Scene choices carry a video badge and an empty file list; the provider draws them at up to 24 fps into a surface capped at 1280 pixels on the long edge and publishes a scaled full-size frame. A session uses the desktop mode for the default presentation and the Lock Screen mode for locked and idle presentations. A bundled catalog may name another directory with `root`; any other catalog may name only its own directory. Media is opened through host file wrappers. A direct read of an external file is logged and is not required. `make build` embeds this extension in `Flua.app`. Setup is described below.

## App build

`make build` produces `build/Flua.app`. It embeds a sandbox-signed copy with identifier `local.flua.desktop.wallpaper`, `FLUALibraryOnly = true` and a file-only read exception for the standard Flua catalog. `FLUA_CATALOG_PATH` can instead bind a build to a disposable absolute catalog path; `FLUA_WALLPAPER_IDENTIFIER` supplies a separate provider identifier for these tests. Launched without `--data-dir`, the application opens that catalog’s directory. It checks that its library matches this path before setup. Only macOS 27 exposes setup.

**Set Wallpaper** in the inspector registers the current containing app and extension, verifies the registered path and applies the saved surface choices for targeted displays directly to macOS. `NativeWallpaperStore` constructs separate Desktop and Lock Screen descriptors with their saved modes and library-owned media URLs; linked surfaces resolve to the same choice. Images are supported and remain still. Unassigned surfaces retain their saved system choice; this does not establish visible mixed-provider rendering on lock. Per Display preserves the global wallpaper as the default fallback and writes targeted overrides, with `$null` for the global override. It validates the private `Index.plist` schema and updates global, display and Space assignments while retaining unrelated metadata. `NativeWallpaper.swift` serializes concurrent Flua applies, saves `NativeWallpaperBackup.plist` in the library, writes atomically and verifies the result. The signed `FluaWallpaperGuard` helper verifies the exact current-user WallpaperAgent executable, pauses it during the transaction and restarts it on commit. EOF, timeout or handled termination resumes it on abandonment. No private Apple entitlement is used.

Application is independent of System Settings discovery or cached choices. macOS owns playback after Flua exits; playlists and Stop remain available in Flua. Stop restores both targeted native surfaces from the baseline retained before Apply, keeping saved Flua assignments. If a previous surface was not saved or its baseline is unusable, Flua silently uses the native macOS default wallpaper for that surface and can capture it as the new baseline. Keep the app and library in place while selected. Settings → Lock Screen → Remove native provider… restores the retained baseline before unregistering this copy. Unavailable baseline surfaces use the macOS default wallpaper during removal too; both wallpaper stores are restored before unregistration. Playback edits automatically refresh matching active choices.

The library-only catalog omits prototype fixtures and uses a separate group ID. When the host acquires a cached choice without fetching settings, the provider loads the current catalog, pushes it and attaches its file watcher. Atomic saves reattach that watcher to the replacement inode, so the sandbox needs no directory-wide file-read exception. Media bytes are still delivered through host file wrappers.

### Playback preferences

The provider monitors power and native fullscreen Spaces independently of Flua. The catalog publishes the current policy; descriptors retain a policy snapshot for a cold start without a readable catalog. A running provider retains its last valid catalog policy across transient read failures. Power pauses cover Desktop and Lock Screen playback. Fullscreen pause covers only Desktop presentation on the host-supplied destination display, and ignores app previews. The [pause rules and verification procedure](../../docs/DEVELOPMENT.md#playback-pause-verification) describe the threshold behavior and remaining hardware checks.

On arm64 macOS 27.0.1 (26A434), a disposable background-only app with only the app-sandbox entitlement ran the production `FSPlaybackEnvironment` helper. It read AC power, 80% battery and Low Power Mode off, matching `pmset`; its fullscreen display UUID matched the active native fullscreen Space and the CoreGraphics display ID. No Screen Recording permission or additional entitlement was needed. This verifies sandboxed observation on the current setup, not physical battery/AC transitions or WallpaperAgent playback.

A separate real WallpaperAgent check on the same OS used a disposable aurora/Animated choice with the containing harness exited and a native fullscreen Space already active. The host supplied `directDisplayID=1`. With host suspension off, enabling fullscreen pause held rendering; an atomic catalog change disabling it resumed frames to 90. Re-enabling it held the count at 362 for about nine seconds, and disabling it resumed that same session. No Flua process was running during these transitions. Apply reported a store-verification error despite the host acquiring the correct descriptor; this check does not establish successful Apply verification. Provider removal completed, and its sole global inheritance-marker difference was restored under the wallpaper guard after checking all other values. Both stores matched the snapshots apart from timestamps, all provider paths matched, and the temporary extension was moved outside its containing app. This verifies live preference changes in an existing fullscreen Space, not fullscreen entry/exit, physical power transitions or multiple displays.

## Build and verify

Run native host procedures that register a provider, change system wallpaper state, or restore wallpaper settings through `scripts/system-test-lock.py`. Hold the lock for the entire procedure, from baseline capture through rollback and final comparison, so other Flua worktrees wait instead of launching tests concurrently. For example: `./scripts/system-test-lock.py "native wallpaper verification" /bin/zsh /path/to/native-wallpaper-check.zsh`. The lock releases when the command exits, including after a crash; that does not establish that system state was restored. `make wallpaper-test` is standalone and does not activate or change system wallpapers, so it does not need the lock.

From the repository root, on a Mac with the Command Line Tools and a macOS 26 or newer SDK/runtime:

```sh
make wallpaper-test
```

Alternatively, run `./Sources/WallpaperExtension/build-and-test.sh`; an optional first argument selects the build directory. The script builds and ad-hoc signs a separate `.appex`, validates its entrypoints and signature/plist, and runs three standalone tests. It performs no extension registration or wallpaper-store edits.

The executable's Mach-O entrypoint must be `_NSExtensionMain`, selected by passing `-Xlinker -e -Xlinker _NSExtensionMain` to `swiftc`. ExtensionFoundation then invokes the retained Swift entrypoint. Starting directly at Swift `main` trapped during real-host initialization. `verify-entrypoint.sh` checks the bootstrap symbol and that Swift `main` survives linking; it rejects an executable built without the linker override.

Verified on arm64 macOS 27.0.1, build 26A434, with the macOS 27 SDK. Deployment target 26.0 is declared but has not been tested on macOS 26. The script builds for the current Mac architecture; Intel execution is unverified.

`provider-self-test` verifies power/fullscreen policy decisions, descriptor fallback, catalog precedence, preview immunity, direct acquire, locked/suspended state update, 64×64 snapshot, settings catalog, and invalidation. `wire-proof` verifies acquire, update, 32×32 IOSurface snapshot, desktop/screen-saver catalog, boxed download status, and invalidation through an anonymous NSXPC listener using Apple's runtime protocol and private secure-coding classes. `media-self-test` verifies image/video creation with nonempty Apple file wrappers, rendered-frame changes, looping, suspension/resume, snapshots and cleanup. It also verifies a power-policy pause holds video frames and time, preserves host suspension, and resumes the saved speed and Animated mode. It also truncates an active copied video in place, checks the failed-session fallback, restores the bytes to the same file and verifies recovery. It draws aurora, cosmos, ocean and ember with no file, including motion, dimming, suspension and a locked Still frame. A 3840×2160 still scene publishes a 3840×2160 surface. These standalone tests run outside the host sandbox, and both wire-test endpoints live in the test process. Real-host results are recorded separately below; standalone success alone does not establish system-host acceptance.

The build script writes the bundle and test results under `Sources/WallpaperExtension/Built/` by default. Sources and the bundled thumbnail are original Flua material.

`media-self-test` also acquires and invalidates an image choice, then creates a fresh provider instance and gives it the same descriptor with a newly created file wrapper. It verifies rendering and unchanged descriptor data. This checks provider reacquisition logic in-process; it does not test WallpaperAgent process relaunch or revocation of a live sandbox token.

### Repeat the discovery check and restore state

This procedure verifies startup and catalog discovery without selecting another wallpaper. Keep the verification directory outside the repository and retain the original store snapshot until cleanup is verified. Before starting, confirm `pluginkit -m -A -D -v -i org.flua.wallpaper.prototype` has no matches; if it already exists, record and preserve that registration instead of applying this cleanup blindly.

1. Run `make wallpaper-test`. Create a fresh directory with `mktemp -d -t flua-native-host`. Save `sw_vers`, the complete output of `pluginkit -m -A -D -v -p com.apple.wallpaper`, and copies of both plists under `~/Library/Application Support/com.apple.wallpaper/Store/`. Record whether `~/Library/Containers/org.flua.wallpaper.prototype` exists. Record the current System Settings page and selected wallpaper. These snapshots contain local settings; keep them out of Git.
2. In that directory, create `FluaHostTest.app/Contents/MacOS/` and `Contents/Extensions/`. Copy the built `FluaWallpaperExtension.appex` into `Contents/Extensions/`; do not modify generated repository output. Create the containing application's `Contents/Info.plist` with `CFBundleIdentifier = org.flua.wallpaper.host-test`, `CFBundleExecutable = FluaHostTest`, `CFBundleName = Flua Host Test`, `CFBundlePackageType = APPL`, `CFBundleVersion = 1` and `LSMinimumSystemVersion = 26.0`. Compile a disposable Swift executable containing `import Foundation` and `print("Flua disposable provider host")` with `xcrun swiftc`, naming the output `Contents/MacOS/FluaHostTest`. The executable need not run for discovery.
3. Create a plist containing only the boolean entitlement `com.apple.security.app-sandbox = true`. Sign the copied extension with `codesign --force --sign - --entitlements <entitlements.plist> <extension-path>`, then sign the containing application with `codesign --force --sign - <app-path>`. This is the tested ad-hoc sandbox setup, not a proven production signature.
4. Register the containing app, then its extension, using the commands below. Set `FLUA_HOST_CHECK_APP` to the absolute disposable app path first.

    ```sh
    /System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister \
        -f "$FLUA_HOST_CHECK_APP"
    pluginkit -a \
        "$FLUA_HOST_CHECK_APP/Contents/Extensions/FluaWallpaperExtension.appex"
    pluginkit -m \
        -A -D -vv \
        -i org.flua.wallpaper.prototype
    /usr/bin/log show \
        --last 5m \
        --style compact \
        --predicate 'process == "FluaWallpaperExtension" OR (process == "WallpaperAgent" AND eventMessage CONTAINS[c] "org.flua.wallpaper.prototype")' \
        --info --debug
    ```

5. Inspect System Settings → Wallpaper without selecting anything. If the catalog arrives after the page opens, navigate away and back to refresh it. Verify the Flua group and all three fixture names. Save relevant host logs and any new `FluaWallpaperExtension-*.ips` report from `~/Library/Logs/DiagnosticReports/`. The corrected build completed the catalog request and showed the fixtures. Do not interpret registration, connection or catalog delivery as rendered playback. Actual selection needs a separately established restoration procedure.
6. Always unregister the exact disposable extension and containing app, including after failure:

    ```sh
    pluginkit -r \
        "$FLUA_HOST_CHECK_APP/Contents/Extensions/FluaWallpaperExtension.appex"
    /System/Library/Frameworks/CoreServices.framework/Frameworks/LaunchServices.framework/Support/lsregister \
        -u "$FLUA_HOST_CHECK_APP"
    pluginkit -m \
        -A -D -v \
        -i org.flua.wallpaper.prototype
    ```

7. Confirm no prototype matches and compare the complete provider path list with the baseline. Rename the disposable app to a suffix other than `.app` to avoid rediscovery. If this run created the prototype sandbox container, move only that new container into the verification directory after the process exits; preserve any pre-existing container. Return System Settings to its original page. Compare both wallpaper plists structurally with the snapshots. The discovery-only run changed only system-maintained `LastUse` timestamps; playback selection also changed `LastSet`. Leave timestamp updates intact. All choices, configurations and other values must match the intended baseline before claiming restoration.

### Playback, scoped files and restoration

Before selecting a fixture, verify that the baseline image actually exists and is readable. A stale image entry in System Settings can silently fall back to a different picture. Record every Space/display and idle assignment from both store plists, not just the visible selection. If the baseline is invalid, establish an agreed readable baseline before proceeding. Do not overwrite concurrent user changes.

For the external-file check, use a disposable source copy and the separate `org.flua.wallpaper.scoped-probe` identifier in both the extension plist and catalog descriptors. Copy the original still/video fixtures outside the containing application and extension. Change only that copy's media choices to advertise the corresponding file URL in the descriptor's `files` array, and encode `{"version":1,"kind":"video","fileIndex":0,"fit":"fill"}` (or `kind:"image"`) instead of `source:"bundle"`. In the sandboxed catalog handler, attempt a direct read of the external fixture before selection and record whether it succeeds. Build and run `make wallpaper-test` from the disposable copy before registering it. These probe URLs and source changes must not enter the production catalog or Git.

After registration, wait for the catalog reply and refresh the Wallpaper page before choosing a fixture. Verify the launched executable's path in host logs: macOS may retain an old extension record or catalog after a temporary registration is replaced. Reopen System Settings or restart WallpaperAgent after registering the current build if necessary. A selected label alone does not prove the current descriptor was used. For the external fixture, require a failed unscoped read, successful acquisition with `scopedFiles=1, activeScopes=1`, and continued frame/loop progress. The prototype logs frame milestones at 2 and 90 and numeric locked/idle flags. Launch the disposable containing executable and let it exit, then verify continued rendering. An actual Lock Screen check requires the user to unlock the Mac and confirm visible motion; an `idle=1` preview is not a screen-saver test.

Restore test selections before unregistering the provider. UI restoration must be checked against both saved plists; a label change alone can leave a stale assignment in another Space. The verified fallback was to read the user-owned WallpaperAgent PID from `launchctl print gui/$(id -u)/com.apple.wallpaper.agent`, stop that exact process with `SIGSTOP`, atomically replace only test-provider choice dictionaries with their saved baseline values, and terminate the stopped process with `SIGKILL` so launchd restarts it from the restored store. Always release or restart the stopped process on failure. Preserve unrelated values and timestamp updates. Do not disable SIP or unload the protected launch agent. Then unregister the exact test bundles as above, verify both identifiers have no PlugInKit matches, compare provider paths and compare both store plists apart from `LastUse`/`LastSet`. In the playback check `Index_v2.plist` was unchanged and `Index.plist` differed only in those timestamps. A provider group may remain in an already-open Settings page until its cached catalog is refreshed.

## Files

- `EntryPoint.swift`: public ExtensionFoundation `AppExtension` and `ConnectionHandler` entrypoint.
- `verify-entrypoint.sh`: verifies the executable starts at `_NSExtensionMain` and retains Swift `main`.
- `Provider.m`: runtime protocol wiring, secure-coding adapters, lifecycle handlers, catalog, and direct tests.
- `MediaRenderer.m/.h`: independent image/video renderer, IOSurface frame delivery, loop handling and scoped-file lifetime.
- `generate-fixtures.m`: creates original still/motion assets for the bundle and tests.
- `wire-proof.m`: independent anonymous-XPC integration test.
- `Info.plist`: separate identifier `org.flua.wallpaper.prototype`, package type `XPC!`, and extension point `com.apple.wallpaper`.
- `PROTOCOL.md`: payload formats, implementation design, and remaining work.

The prototype uses private Apple interfaces discovered in the local system framework. Their names and formats may vary between OS releases. The disposable ad-hoc sandbox signature was sufficient for the observed startup, scoped media access and rendering on the tested OS; other OS versions remain unverified.

### Mixed Apple and Flua content investigation

A normal ad-hoc-signed host probe resolved Apple's Sonoma extension through LaunchServices. Its extension identity declares `com.apple.private.wallpaper.extension-host` as a required host entitlement. Ordinary ExtensionFoundation discovery returned no wallpaper extensions, and its monitor reported “Host is not entitled observe.” A lower-level XPC connection launched the extension but was invalidated before the settings request returned a model (`NSCocoaErrorDomain` 4099). Repeating with the full exported host callback interface and an empty content-type set produced the same invalidation. Both wallpaper stores and provider registration paths remained unchanged. The invalidation alone does not prove its cause, but no usable ordinary-host connection was established. Flua does not request Apple's private host entitlement. Live mixed-provider rendering remains unsupported; copying a snapshot would preserve only a still frame, not Apple's animation.
